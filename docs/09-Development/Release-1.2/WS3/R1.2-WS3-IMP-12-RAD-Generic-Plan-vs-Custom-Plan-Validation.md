## 1. What This Card Is Testing, in One Sentence

`AR-09` (read in full before drafting this) closed the "can Postgres use these indexes at all" question for good — the standalone, literal-embedded query got a `BitmapOr` → two `Bitmap Index Scan`s → `Parallel Bitmap Heap Scan` plan, 1,340 buffers, 660ms, unambiguous index-accelerated execution. The remaining, narrower question is whether `search_geo_places()` — because it's a non-inlined SQL function, so its argument is planned as a generic, type-only parameter rather than the actual search string — is stuck reusing one fixed "generic" plan regardless of what's searched, while an ad hoc literal query gets a fresh "custom" plan informed by the real value's selectivity every time. This card's Task 4/5 framing (flat buffers on the function side vs. varying buffers on the standalone side) is exactly the smoking-gun test `AR-09` §3 Step 2 already proposed — this card extends it from Kotagiri-only to a 5-term set and adds the full-pipeline literal comparison per term, not just the one branch `AR-09`'s own screenshot evidenced.

## 2. Task 1 — Capture Standalone Plan (Full Pipeline, Literal-Embedded, All 5 Terms)

**Full pipeline, not just the name branch** — structurally identical to `search_geo_places()`'s actual body (`AR-09` §3 Step 1), with the search term spliced in as a literal instead of passed as a parameter. One block per term; only the literal string changes between them.

### Kotagiri

```sql
explain (analyze, buffers, format text)
with normalized as (
  select public.immutable_unaccent(lower(trim('Kotagiri'))) as q
),
name_matches as (
  select p.id as geo_place_id, null::text as matched_alias,
    case when public.immutable_unaccent(lower(p.ascii_name)) like (select q from normalized) || '%' then 2.0
         else similarity(public.immutable_unaccent(lower(p.ascii_name)), (select q from normalized)) end as match_score
  from public.geo_places p
  where public.immutable_unaccent(lower(p.ascii_name)) like (select q from normalized) || '%'
     or public.immutable_unaccent(lower(p.ascii_name)) % (select q from normalized)
),
alias_matches as (
  select a.geo_place_id, a.alias_text as matched_alias,
    case when public.immutable_unaccent(lower(a.alias_text)) like (select q from normalized) || '%' then 1.9
         else similarity(public.immutable_unaccent(lower(a.alias_text)), (select q from normalized)) end as match_score
  from public.geo_aliases a
  where public.immutable_unaccent(lower(a.alias_text)) like (select q from normalized) || '%'
     or public.immutable_unaccent(lower(a.alias_text)) % (select q from normalized)
),
combined as (select * from name_matches union all select * from alias_matches),
best_per_place as (
  select distinct on (geo_place_id) geo_place_id, matched_alias, match_score
  from combined order by geo_place_id, match_score desc
)
select p.id, p.name, p.place_type, p.country_code, p.admin1_name, p.admin2_name, p.population, b.matched_alias, b.match_score
from best_per_place b
join public.geo_places p on p.id = b.geo_place_id
order by b.match_score desc, p.population desc nulls last, p.name asc
limit 8;
```

## 5. Task 4 — Evaluate Buffer Behaviour (Function Side)

**What this is testing, stated in advance so the result is legible immediately:** `AR-09` §3 Step 2 already named this the direct confirming test — if Task 2's buffer counts stay at or near the current ~14,335 baseline across all 5 genuinely different search terms (different string lengths, different match-set sizes, a European name in `Zermatt` vs. Indian city names in the other four), that is strong, direct evidence of one fixed, generic plan being reused regardless of the argument — the function isn't re-costing the query per call, it's running the same plan every time. **Meaningful variation** in buffer counts across terms would weaken or refute the generic-plan theory and should be reported exactly as observed, not smoothed over — per this card's own evidence-only framing, an unexpected result here is just as reportable as a confirming one.
