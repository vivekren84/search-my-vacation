```sql
explain (analyze, buffers, format text)
with normalized as (select public.immutable_unaccent(lower(trim('Kotagiri'))) as q)
```

## 4. Task 3 — Forced Planner Investigation

**Exactly as `AR-08` Section 3 Step A specifies**, scoped to one read-only transaction — nothing persists, no data or schema is touched, and `ROLLBACK` guarantees `enable_seqscan` reverts immediately regardless of outcome:

```sql
begin;
set local enable_seqscan = off;

explain (analyze, buffers, format text)
with normalized as (select public.immutable_unaccent(lower(trim('Kotagiri'))) as q)
select p.id,
  case when public.immutable_unaccent(lower(p.ascii_name)) like (select q from normalized) || '%' then 2.0
       else similarity(public.immutable_unaccent(lower(p.ascii_name)), (select q from normalized)) end as match_score
from public.geo_places p
where public.immutable_unaccent(lower(p.ascii_name)) like (select q from normalized) || '%'
   or public.immutable_unaccent(lower(p.ascii_name)) % (select q from normalized);

rollback;
```

**Interpretation, stated in advance so the result is legible the moment it comes back (per `AR-08` §3 Step A):** if the plan still shows `Seq Scan on geo_places` even with sequential scan forcibly disabled, no index-based plan exists for this predicate at all — a recognition/eligibility failure, not a cost judgment. If it flips to `Bitmap Heap Scan` referencing `geo_places_ascii_name_unaccent_trgm_idx`, the index is usable and the planner is making a cost-based choice to avoid it under normal settings.

**Extending this to the alias branch — not explicitly named in `AR-08`, but this card's Task 3 says "the same query" and Task 2 above establishes the alias branch is being tracked in parallel, so I'm including the analogous forced check for completeness rather than leaving it asymmetric:**


## 7. Task 6 — Planner Interpretation (Evidence Only — Not Resolved)

Per this card's explicit instruction ("Document evidence only. Do not recommend implementation"), the three possible outcomes are framed below exactly as the card states them, each tied to which specific result from Tasks 1–5 would support it. None is selected yet.

**Outcome A — Planner cannot produce an index plan.** Supported if Task 3's forced run (`enable_seqscan = off`) *still* shows `Seq Scan` for either or both tables. This would mean no index-based plan exists at all for this predicate shape — a recognition/eligibility failure, not a cost judgment (`AR-08` §2 Q5/Q6, hypothesis #5: expression index selectivity or a silent recognition failure).

**Outcome B — Planner produces an index plan but rejects it.** Supported if Task 3's forced run *does* show `Bitmap Heap Scan` against the new indexes (proving a valid plan exists), while Task 1/2's unforced baseline still chooses `Seq Scan`. This is `AR-08`'s own leading hypothesis (§0/§4): a legitimate cost-based decision, most likely driven by the tables being fully cache-resident (zero disk reads in every buffer measurement across this entire investigation) combined with GIN's mandatory heap recheck overhead for the lossy `%` operator — meaning the planner may be correctly deciding the index isn't worth it at this scale, not malfunctioning.

**Outcome C — Planner selects different plans for different predicates.** Supported if Task 4's Query A and/or Query B (isolated `LIKE`-only or `%`-only) produce an index scan under normal settings while Task 1's combined `OR` form does not — this would isolate the `OR` combination itself as the differentiator (`AR-08` §2 Q2/Q4), independent of whether Outcome A or B also holds.

These are not mutually exclusive in principle (e.g., Outcome B and Outcome C could both be true — a cost-based rejection *of the combined form specifically*, while each isolated predicate is cheap enough to win on its own).
