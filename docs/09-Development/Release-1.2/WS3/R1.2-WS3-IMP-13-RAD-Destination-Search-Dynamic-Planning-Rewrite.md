## 1. Engineering Summary — Implementation Approach

### 1.1 What changed, precisely

`search_geo_places()` moves from `LANGUAGE SQL` to `LANGUAGE PLPGSQL`. The function body now:

1. Normalises the input once — `public.immutable_unaccent(lower(trim(search_query)))` — identical expression and order of operations to the previous version's `normalized` CTE, just computed once as a PL/pgSQL variable instead of once per row inside a subquery.
2. Builds the exact same CTE query (`name_matches` → `alias_matches` → `combined` → `best_per_place` → final join/order/limit) as a text string via `format(...)`, with the normalised search term and its prefix-match pattern spliced in through `%L` (safe literal quoting) at the two points the old query referenced `(select q from normalized)`, and the clamped `LIMIT` value spliced through `%s` (no quoting needed — it's already a typed `int`, not user text).
3. Executes that freshly-built string via `return query execute sql_text`.

**Why this fixes the problem (`AR-09`/`AR-10`):** the previous version was a non-inlined `LANGUAGE SQL` function — non-inlining forced by its own load-bearing `set statement_timeout to '2000'` clause. A non-inlined SQL function's body is planned once, with its argument represented as an opaque parameter, not the literal value — so the planner's `%`/`LIKE` selectivity estimation had nothing real to work from and fell back to one fixed, generic plan regardless of what was searched. `AR-10`'s evidence proved this directly: literal-embedded execution varied 180ms–2018ms across three terms tracking real selectivity, while the function itself stayed flat at ~3.7–4.0s / ~14.3K–14.7K buffers regardless of which of those terms was called. By building and executing a *fresh* SQL string on every call — with the real search term already spliced in as a literal before that string is ever parsed — each call now gets its own statement, planned fresh against the real value, exactly matching the conditions that produced the efficient literal-embedded benchmarks.

### 1.2 Rationale for each specific choice

- **`format(...)` with `%L`, not string concatenation:** this card's Technical Requirement 3 explicitly requires a safe construction technique and explicitly forbids concatenated user input. `%L` is Postgres's own built-in safe-literal-quoting specifier (equivalent to `quote_literal()`) — it correctly escapes embedded quotes/backslashes in the search term, giving the same injection-safety guarantee class as parameter binding, just via literal-escaping instead of protocol-level binding, per `AR-10` §2 Q4's own framing.
- **`%s` for the `LIMIT` value, not `%L`:** `limit_value` is already a typed `int` at the function boundary (Postgres's own type system guarantees it, not user-supplied text), so there's no injection surface to guard against there, and `%s` avoids an unnecessary (though harmless) string-quote-then-implicit-cast round trip that `%L` would otherwise produce for a numeric value.
- **Normalisation computed once in PL/pgSQL, not repeated per branch inside the dynamic SQL:** the old CTE query referenced `(select q from normalized)` four times per branch (two branches). Computing `normalized_query`/`prefix_pattern` once, up front, and splicing the resulting literal in at each of those same points is behaviourally identical (same deterministic value every time) and marginally simpler — it also means the literal reaches the planner directly, with no subquery indirection at all.
- **Dollar-quoting (`$func$` for the outer function body, `$sql$` for the inner dynamic-SQL template):** two different tags, so there's no ambiguity between the function's own body delimiter and the string literal it builds — the standard, safe PostgreSQL pattern for a PL/pgSQL function that itself constructs a `$$`-quoted dynamic SQL string.
- **`stable`, not `volatile`:** the function still performs only read-only `SELECT`s (via dynamic SQL); `STABLE` remains the correct, most restrictive-and-accurate volatility category, unchanged from the previous version.
- **`SECURITY INVOKER` (unchanged, by omission — the default):** no `SECURITY DEFINER` introduced, consistent with `ARCHIE-R1.2-WS3-AR-01`'s original recommendation and every version of this function since.
- **`set statement_timeout to '2000'` preserved exactly, not dropped or altered:** `AR-10` explicitly flagged this as something to re-declare rather than assume carries over — PL/pgSQL functions support the identical function-level `SET` clause syntax, so it's preserved verbatim, same value, same mechanism. See §4 for why this specific value needs live re-verification, not because the migration is uncertain about it, but because the evidence trail itself has an open question here.

### 1.3 Compatibility considerations

- **RPC signature:** `search_geo_places(search_query text, result_limit int default 8) returns table (...)` — byte-identical. `create or replace function` with an unchanged signature preserves existing grants automatically (confirmed by direct grep of the new migration file: zero `grant`/`revoke` statements appear anywhere in it, matching the pattern already established and confirmed in `IMP-09`).
- **Frontend/`web/lib/geo-validation/repository.ts`:** not touched, and doesn't need to be — its `toGeoSearchResult()` field mapping (`geo_place_id`, `canonical_name`, `place_type`, `country_code`, `admin1_name`, `admin2_name`, `population`, `matched_alias`, implicitly `match_score` for ordering) matches this migration's unchanged return columns exactly, same confirmation already made in `IMP-09` §2 Task 4 and re-verified here by re-reading the return-table clause against that file — no drift.
- **PostgREST/Supabase RPC compatibility:** unaffected — `PL/pgSQL` functions are exposed as RPCs identically to `LANGUAGE SQL` functions from PostgREST's perspective; nothing about the calling convention changes.

## 7. Risk Assessment

- **Correctness risk:** Low — the dynamic query text is a direct, line-for-line preservation of the previous version's CTE logic (diffed by construction, not rewritten from memory, per `AR-09` §5's own flagged implementation risk), with only the literal-delivery mechanism changed. The regression set in §5 is what confirms this empirically rather than by inspection alone.
- **SQL injection risk:** None introduced — `%L` provides the same safety guarantee as bound parameters; the only unquoted splice (`%s` for `limit_value`) is a typed integer, not text, so there is no string-injection surface there.
- **Maintainability cost:** Real and named, not hidden — `AR-10` §2 Q5 already flagged this: dynamic SQL is inherently harder to audit at a glance than static SQL. Mitigated here by keeping the query template as a single, clearly-commented `format(...)` call, with the header comment documenting exactly what changed and why, so a future reader isn't reverse-engineering the rationale.
- **Timeout behaviour:** Genuinely unresolved until §4's results come back — flagged, not assumed either way.
- **Parallel execution:** Not explicitly addressed by this migration (no `PARALLEL SAFE` marking added, matching the previous version, which also had none) — `AR-09` §1's own secondary factor (a `Function Scan` over a non-inlined function generally isn't parallel-eligible from the *caller's* side) may still apply to the outer call; whether the *inner*, dynamically-executed statement gets its own parallel plan is something the benchmark's actual execution plan output will show, not something I can guarantee from the SQL text alone. If §3's results show meaningfully improved-but-not-fully-target-hitting numbers, this is the first place I'd look next — not proposed as a change here.
- **Rollback:** Documented in the migration file itself — reverting means re-running the prior `LANGUAGE SQL` definition from `20260829130000_...sql`, a clean, safe replace since the signature never changes either direction.
