# Purpose

This document records the major milestones, releases, architectural decisions, and evolution of the Search My Vacation platform.

Unlike release notes, which focus on individual releases, this document provides a chronological history of the product and serves as the institutional memory of the project.

The document is intended to evolve alongside the platform and be updated after every significant release.

---

# Project Vision

Search My Vacation was created with a simple belief:

> **Every traveller is unique. Every journey should be too.**

The platform focuses on designing personalised travel experiences instead of selling standard travel packages.

The long-term vision is to build a technology-driven travel platform that combines human expertise, intelligent recommendations, and exceptional traveller experiences.

# Release 1.2 — Completed (Retrospective Entry)

*Note on continuity: the "Release 1.2" section earlier in this document (Primary Objectives, Initial Candidate Improvements) was written on 16-Aug-2026, before implementation began, and is preserved above unchanged as a historical record of the original plan. This section is the completed-release retrospective entry, added at Release 1.2's close per this document's own "review and update after every significant release" maintenance instruction.*

## Release Overview

Release 1.2's high-level objective was to raise the premium quality and trustworthiness of the traveller-facing experience while strengthening the data and verification layers beneath it: sharpen the homepage's visual and information hierarchy, resolve the overlap between the Experiences section and the Journey Mood/Journey Passport model, evolve Destination Intelligence toward a weighted, evidence-based recommendation model, close known Journey Passport entry-context defects, verify traveller phone numbers internationally via OTP before lead capture, and replace free-text destination entry with a validated autocomplete grounded in a real geographic dataset. Major product goals: preserve the "every traveller is unique" positioning while removing friction and data-quality gaps identified during Release 1.1; extend international reach (E.164 phone support); and reduce fraudulent or low-quality Journey Passport submissions through OTP verification, all without compromising the deterministic, non-generic-AI nature of the Journey Director recommendation engine.

## Workstreams Completed

### WS1 — Homepage Premium Visual Refinement
Refined the mood-card illustration palette toward ivory/champagne tones, reduced gold saturation, and kept the Hero as the dominant homepage element — a targeted visual pass rather than a full redesign. Independently re-confirmed via a dedicated Homepage Architecture Validation Review (Product/IA and UX/Visual Hierarchy) before Workstream 3 began.

### WS2 — Experiences vs Journey Mood Rationalisation
Resolved the overlap between the Experiences section and the Journey Mood/Journey Passport model by retiring Experiences from public navigation and the homepage, while deliberately preserving its implementation, assets and code for possible future reuse — no deletion, no URL removal.

### WS3 — Destination Intelligence
Introduced weighted Primary/Secondary/Tertiary destination-preference ordering as the preferred Journey Director recommendation model, governed by a dedicated architecture decision record. Delivered the Phase 0–2 native-ID implementation chain (governance foundations, Operational Steward appointment, generation and vocabulary alignment) and, later in the release, diagnosed and resolved a significant destination-search performance and reliability problem down to root cause (PostgreSQL planner/index behaviour on `search_geo_places`), closing it with a dynamic-planning rewrite. Phase 3 (Runtime Alignment) and Phase 4 (Recommendation Behaviour) were explicitly scoped out and deferred, not implemented, under Release 1.2.

### WS4 — Journey Passport Entry Context Improvements
Resolved known entry-context defects across the Romance, Companion, and Pace & Timing paths, and added traveller-name field validation to reject numeric characters while permitting letters, spaces, hyphens and apostrophes.

### WS5 — International Phone Number & OTP Verification
Added E.164 international phone number support (via `libphonenumber-js`) across capture points, and required successful mobile OTP verification before a Journey Passport submission completes, scoped to Journey Passport only. Selected MSG91 as the SMS provider behind an internal abstraction interface so the provider can be replaced without touching Journey Passport business logic. Carried the feature through implementation, a ten-task independent engineering review, and — after navigating India's DLT regulatory registration chain for the Principal Entity, Sender Header and Template, including a previously-undocumented Principal Entity–Telemarketer chain requirement — a confirmed live, end-to-end production OTP send-to-verification cycle.

### WS6 — Journey Passport Destination Autocomplete & Validation
Replaced free-text destination entry with a searchable, multi-select autocomplete validated against a free geographic dataset (GeoNames), explicitly excluding paid destination APIs for this release. Preserved Journey Director as the sole authority for served-destination validation — the autocomplete only confirms a place is real, not that SMV serves it. Delivered across eight implementation phases (foundation through accessibility/interaction validation and final handover), independently functionally validated and traveller-experience validated, and closed with Product Owner acceptance.

### WS7 — Documentation & Governance
Established Release 1.2's governance discipline: architecture decision records, a formal Product Decision Log embedded in the release tracker, independent multi-persona review chains (engineering → functional QA → traveller experience), a governance backlog for Release 1.3, and a provider dependency register. This workstream remained in progress as this entry was written — a documentation-completeness audit and a governance-reference reconciliation identified and worked to close gaps between work performed and work committed to the repository, including this document's own recovery. **Correction, `EBC-R1.2-WS7-08`, 31-Aug-2026:** this passage originally cited that audit, reconciliation and recovery as `EBC-R1.2-WS7-AUD-01`, `EBC-R1.2-WS7-GOV-01` and `EBC-R1.2-WS7-IMP-01` respectively; independently reconfirmed that none of the three exist as repository documents or commits (see `docs/10-Backlog/RELEASE-1.2.md`, `RISK-R1.2-014`). The underlying work and findings described are not disputed and are not rewritten by this correction — only the fabricated citations are removed. The subsequent tracker reconciliation this audit called for was carried out and committed under `EBC-R1.2-WS7-06` (Release 1.3 backlog carry-forward) and `EBC-R1.2-WS7-07` (Release 1.2 tracker reconciliation); this correction itself was made under `EBC-R1.2-WS7-08`. ## Major Technical Achievements

**Destination Intelligence evolution.** Moved from an unweighted destination-matching model to a governed, weighted Primary/Secondary/Tertiary preference model, with a native-ID generation and vocabulary-alignment pipeline brought under explicit architectural and operational ownership (an appointed Destination Operational Steward) rather than left as an unowned artefact.

**Geo validation.** Replaced free-text destination entry with autocomplete validated against a self-hosted GeoNames dataset (`geo_places`/`geo_aliases`), and separately diagnosed and resolved a serious query-performance regression in `search_geo_places` traced to PostgreSQL planner and expression-index behaviour — a multi-stage architecture investigation that ended in a dynamic query-planning rewrite rather than a narrow index tweak.

**Journey Director improvements.** Preserved Journey Director as the sole served-destination authority throughout both the destination-autocomplete and destination-intelligence changes, protecting the existing recommendation guardrail established in Release 1.1 rather than letting new input surfaces implicitly expand it.

**Journey Passport enhancements.** Closed known entry-context defects (Romance, Companion, Pace & Timing paths) and added traveller-name validation, improving Journey Passport data quality without changing its core structure.

**OTP verification.** Delivered a fail-closed OTP architecture — the provider integration returns a `not-configured` state rather than erroring when credentials are absent — which let engineering build, review and functionally validate the entire OTP flow before the external MSG91/DLT dependency was live, and cleanly separated "engineering complete" from "operationally deployable" throughout the release.

**Governance evolution.** See the dedicated section below.

**Architecture maturity.** Two Release 1.2 Architecture Decision Records were drafted and ratified (Destination Knowledge Governance; DLT External Provider Onboarding), each converting decisions already made in practice into permanent, reusable architecture records — a discipline not consistently present in earlier releases.

## Governance Evolution

Release 1.2 introduced or matured several governance practices worth carrying forward as standing conventions rather than one-release artefacts:

- **ADR usage.** Architecture decisions material enough to outlive a single EBC (destination knowledge governance, external-provider/DLT onboarding) were captured as standalone Architecture Decision Records under `docs/20-Architecture/`, reviewed and ratified separately from the implementation work they governed.
- **EBC process maturity.** The Evidence-Based-Change model matured into a consistent multi-persona chain per significant change — architecture review, implementation, independent engineering re-review, functional QA, and traveller-experience validation each performed by a different persona, none approving its own work.
- **Architecture reviews.** Workstream 3's destination-search performance investigation alone produced an eleven-part architecture review series before reaching its final recommendation, reflecting a deliberate preference for evidence over speed when diagnosing a production-quality issue.
- **QA independence.** Functional QA (Keerthi) was consistently run as a separate, reproducible validation pass against acceptance criteria, distinct from and after engineering's own technical validation — including a ten-task independent engineering review for Workstream 5 before functional QA began at all.
- **Traveller validation.** Traveller-experience review (Sri) was run as its own independent pass on Workstreams 4, 5 and 6, evaluating clarity, trust and emotional quality separately from functional correctness.
- **Governance backlog.** A dedicated `RELEASE-1.3-GOVERNANCE-BACKLOG.md` was introduced to hold governance and operational-playbook recommendations (for example, generalising the DLT onboarding experience to future external-provider integrations) separately from ordinary product/technical-debt backlog items, plus a first Provider Dependency Register consolidating operational knowledge about every external provider the platform relies on.
- **Release 1.3 planning.** Engineering observations accepted-but-deferred during review were consistently converted into tracked Release 1.3 technical-debt items rather than silently dropped or implemented out of scope.
- **A documentation-location lesson, still being closed as this entry is written:** a meaningful share of Release 1.2's EBC evidence — architecture-review detail, independent validation reports, and in two workstreams' cases (WS4, WS6) the entire documented workstream — was authored during AI-assisted delivery sessions but not committed into this repository, leaving the versioned repository unable to fully reconstruct the release's governance trail on its own. Workstream 7's documentation audit and governance reconciliation exist specifically to identify and close that gap; see Lessons Learned below.

## Lessons Learned

**Delivery.** Splitting review authority across personas (engineering → independent engineering re-review → functional QA → traveller experience) surfaced defects that a single pass would likely have missed — including a database-function defect only detectable against a live schema, not through code review or static analysis. Compressing that sequence to save time would have traded away exactly the kind of finding it exists to catch.

**Engineering.** Designing external-dependency integrations to fail closed (refuse to act rather than behave unpredictably when a dependency isn't configured) let engineering work proceed independently of that dependency's own timeline — in Workstream 5's case, an external regulatory approval chain with no committed SLA from any party outside the project.

**Governance.** A regulatory or provider-approval dependency and a local configuration error can present identically as the same class of failure; a team should verify configuration directly against provider documentation before attributing a persistent failure entirely to an external dependency still in progress, even when that dependency is also genuinely still pending. Institutional knowledge about a multi-step external onboarding process (the DLT Principal Entity–Telemarketer chain, in this case) is easy to lose to informal channels if it isn't captured as a reusable runbook the first time it's learned.

**AI collaboration.** Operating through separated personas, each with a defined mandate and explicit boundaries on what it may approve, kept "engineering says it's done" from being mistaken for functional or traveller-experience sign-off — but did not, by itself, guarantee that documentation produced across many working sessions ended up in the versioned repository where anyone without that specific session's context could find it. Treating "the record exists" and "the record is committed" as the same thing was Release 1.2's clearest documentation-process lesson.
