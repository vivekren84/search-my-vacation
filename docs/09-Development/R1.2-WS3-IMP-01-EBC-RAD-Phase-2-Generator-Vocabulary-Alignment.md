## 4. Executive Summary

Phase 2 implements the two controls approved as WP-4 and WP-5 in `R1.2-03.05`:

1. **KB-to-Operational Reconciliation Check** — add a mechanical, initially non-blocking validation step that compares active destinations and regions in the Destination Knowledge Base with the operational workbook, then reports missing operational representation as a named, non-suppressible generation finding.
2. **Generator Label Mapping Alignment** — report controlled-vocabulary reachability and, only where the approved vocabulary-scope decision and KB-validated operational taxonomy permit it, derive `EMOTION_BY_LABEL`, `THEMES_BY_LABEL`, and `TRAVELLER_BY_LABEL` from that operational source instead of maintaining their scope manually.

This work strengthens the boundary between the approved Business Layer and the existing Generation Layer. It does not replace the workbook, redesign the generator, introduce a general vocabulary registry, add a schema framework, or alter runtime recommendation logic.

The existing deterministic, checksummed, atomic generation mechanics remain in place. The existing `journeyBaseStatus === "Yes"` eligibility filter remains unchanged. Generated output must not be promoted until regression evidence has been reviewed and Archie has passed the Phase 2 review gate.

## 5. Background and Problem Statement

The approved WS3 audits identified three separately maintained representations of destination intelligence:

```text
Destination Knowledge Base (Business Layer)
                    ↓
Operational workbook (Operational Layer)
                    ↓
Journey Intelligence Generator (Generation Layer)
                    ↓
Generated JSON and runtime label mappings
                    ↓
Journey Director runtime
```

The pipeline itself is deterministic and already validates workbook structure, generated artefacts, checksums, references, and repeatability. The problem is not a defective generator architecture. The gap is that:

- no mechanical check confirms every KB-active destination or region has an operational-layer row or an approved exception;
- the generation report does not expose that reconciliation state as a distinct governance finding;
- the operational taxonomy currently exposes only a subset of the KB-controlled vocabulary;
- runtime label mappings are hand-authored in `release1Candidates.ts`, so their scope can silently reflect an older workbook taxonomy; and
- changing those mappings can alter recommendations for existing candidates, creating the approved **Medium–High** regression risk.

At the approved planning baseline, controlled-vocabulary reachability was measured as:

| Vocabulary | KB-approved | Operational / reachable baseline | Gap |
| --- | ---: | ---: | ---: |
| Traveller Types | 9 | 5 | 4 |
| Emotions | 17 | 10 reachable runtime IDs from the operational labels | 7 (41%) |
| Themes | 36 | 17 reachable runtime IDs from the operational labels | 19 (53%) |

These measurements are a baseline for reporting and regression comparison, not authority to invent or expand vocabulary values.

## 6. Objectives

This EBC shall:

1. Make KB-to-Operational divergence visible on every controlled generation run.
2. Report missing KB-active destinations and regions distinctly from existing `REVIEW_REQUIRED` records.
3. Launch the reconciliation check in warn-mode, preserving generation while known gaps are resolved or explicitly deferred.
4. Add a promotion-review checkpoint so a successful generation run is not automatically considered promotable.
5. Make Emotion, Theme, and Traveller Type reachability visible in the generation report.
6. Align the three existing runtime label-mapping tables with the KB-validated operational taxonomy, subject to the approved vocabulary-scope branch.
7. Preserve deterministic output, checksum integrity, current generator guarantees, and established layer boundaries.
8. Produce reviewable before/after evidence for Product and Archie before any changed generated output is promoted.

## 7. Approved Implementation Scope

### 7.1 WP-4 — KB-to-Operational Reconciliation Check

#### Objective

Implement the ADR's named governance control that would have surfaced the Amritsar, Assam, Corbett, and Darjeeling operational gaps mechanically rather than through manual audit.

#### In scope

- Add reconciliation logic alongside the existing workbook validation flow.
- Read the active destination and region set from the approved Knowledge Base source defined by the implementation design; do not duplicate or redefine the business list in a new registry.
- Compare that approved set with the operational workbook row set.
- Treat an operational row with any `journeyBaseStatus` value as operational representation for reconciliation purposes; this check does not determine recommendation eligibility.
- Permit a dated, owned exception only where governance records explicitly authorise one.
- Emit a named **KB-to-Operational Reconciliation** section in the generation report.
- List every missing destination or region with stable identity, classification, and disposition status.
- Keep findings visible and non-suppressible in the report while running the check in warn-mode initially.
- Preserve the existing `REVIEW_REQUIRED` warning section and present reconciliation findings separately.
- Add an explicit promotion-review checklist item covering reconciliation results.
- Add isolated tests for no-gap, known-gap, region-gap, and approved-exception cases.

#### Required behaviour

| Condition | Generator result | Report result | Promotion result |
| --- | --- | --- | --- |
| No reconciliation gap | Continue | Named section reports PASS / no gaps | Eligible for remaining review steps |
| Known or approved deferred gap | Continue in warn-mode | Named finding with owner, decision or review reference, and status | Requires reviewer acknowledgement |
| New, unowned, or unexplained gap | Continue in initial warn-mode | Named high-visibility finding; must not be hidden among general warnings | **Not promotable** until dispositioned |
| Reconciliation logic cannot read or compare an authoritative input | Fail the validation step | Actionable error | Not promotable |

#### Explicit boundary

WP-4 adds a check around the existing generation pipeline. It must not change `generateJourneyDNA.ts`'s `journeyBaseStatus === "Yes"` inclusion filter, auto-author workbook rows, or make a business decision about whether a destination is recommendation-ready.

### 7.2 WP-5 — Generator Label Mapping Alignment

#### Objective

Close the approved controlled-vocabulary reachability gap without changing the underlying runtime mapping mechanism or inventing new business vocabulary.

#### In scope

- Add a **Vocabulary Reachability** section to the generation report.
- Report the KB-approved count, operational taxonomy count, mapped runtime count, unmapped labels, and unreachable approved values for:
  - Emotions;
  - Themes; and
  - Traveller Types.
- Validate the operational taxonomy source against the KB-approved lists or an explicitly recorded **Approved Release Scope Reduction**.
- Align the existing `EMOTION_BY_LABEL`, `THEMES_BY_LABEL`, and `TRAVELLER_BY_LABEL` tables with that validated operational source.
- Use deterministic generation or a small generated mapping module within the existing generator/catalogue boundary; do not introduce a general-purpose vocabulary registry.
- Preserve legitimate translation where a workbook label maps to an existing controlled runtime ID; source-of-scope changes, but the mapping responsibility remains.
- Detect duplicate labels, unmapped labels, unsupported target IDs, and non-deterministic ordering.
- Diff all generated candidates and relevant runtime catalogue output against the pre-change baseline before promotion.
- Route any change to an existing candidate's Emotion, Theme, or Traveller Type assignment to Product review and Archie's review gate.

#### Approved decision branch

WP-5 must follow the decision already required by `R1.2-03.05` and the ADR:

| Vocabulary-scope decision | WP-5 implementation |
| --- | --- |
| **Extend toward the KB-approved scope** | First align the operational taxonomy sheets under the proper Product / Operational authority. Then generate the three label-mapping tables from those KB-validated sheets and run the full regression diff. |
| **Approved Release Scope Reduction** to the current subset | Record the decision and named subset, add reachability reporting, and retain the existing mapping tables unless another approved change is necessary. No table regeneration is required merely to reproduce the same reduced scope. |
| No recorded decision | Reachability reporting may be implemented, but changed mapping tables must not be promoted. Escalate to Tiger, Vivek, and Archie. |

#### Explicit boundary

WP-5 must not change `EmotionId` or `ThemeId` unions in `engine.types.ts`; the approved plan records that they already match the KB. A `TravellerType` change is permitted only if the approved Product decision extends the Release 1.2 scope beyond the current five types and Archie confirms the type-level change. No other runtime type or behaviour change is authorised.

## 9. Implementation Approach

### Step 0 — Confirm authority and planned files

- Re-read the current `R1.2-03.05`, ADR, KB, Phase 1B report, operational workbook metadata, generator entry point, validation flow, report writer, and label-mapping consumers.

### Step 1 — Capture the pre-change baseline

- Record the operational workbook checksum and generated manifest checksum.
- Capture current reconciliation results, including known deferred destinations and regions.
- Capture the current 9/17/36 approved vocabulary counts and the operational/reachable subset.
- Preserve the three existing mapping tables for direct comparison.
- Run the relevant existing generator, runtime-catalogue, and determinism verification commands before changing code.

### Step 2 — Implement WP-4 reconciliation

- Add a focused reconciliation result model.
- Compare KB-active destination/region identities with operational rows and approved exceptions.
- Integrate the check into the existing validation/orchestration flow.
- Add the named, non-suppressible report section.
- Keep warn-mode separate from promotion eligibility: generation may finish, but unexplained results block promotion.
- Verify no change to the Journey Base eligibility filter or generated candidate construction.

### Step 3 — Implement WP-5 reachability reporting

- Calculate approved, operational, mapped, unmapped, and unreachable sets for Emotions, Themes, and Traveller Types.
- Add deterministic, review-friendly tables to the generation report.
- Treat every unapproved label or target ID as a visible finding; do not normalise it by inventing a new value.

### Step 4 — Align mapping source where authorised

- If the approved scope is extended, generate the three mapping tables from the KB-validated operational taxonomy.
- Keep mappings typed against the existing runtime IDs.
- Fail focused mapping generation on duplicate source labels, unsupported target IDs, or ambiguous translations.
- If Release 1.2 formally retains the reduced subset, document that decision and do not create a generated table merely to mimic the existing constants.

### Step 5 — Regenerate and compare

- Run the generator against the approved operational workbook in a controlled pass.
- Verify artefact integrity, manifest checksums, record counts, and deterministic repeatability.
- Produce a semantic diff of candidate Emotion, Theme, and Traveller Type assignments, not only a file-level diff.
- Separate expected additions from changes to existing candidates.
- Treat any unexplained existing-candidate change as a promotion blocker.

### Step 6 — Review and promote

- Assemble the reconciliation report, reachability report, generated artefact diff, verification results, and rollback reference.
- Obtain Product disposition for candidate-assignment changes.
- Submit the full evidence bundle to Archie.
- Promote only after the review gate in §12 passes.

## 10. Validation and Regression Strategy

### 10.1 Focused validation

- Reconciliation check: no-gap, missing destination, missing region, approved exception, malformed/duplicate identity, and unreadable authoritative source.
- Reachability: full reach, reduced approved scope, unmapped operational label, unreachable KB-approved value, duplicate label, invalid target ID, and stable ordering.
- Report generation: both new sections always render, including zero-finding cases.

### 10.2 Existing repository verification

Run the existing relevant checks from `web/`, including:

- `npm run build:journey-intelligence-generator`
- `npm run verify:journey-intelligence`
- `npm run verify:journey-intelligence:determinism`
- `npm run verify:journey-intelligence:runtime`
- `npm run verify:journey-intelligence:steering`
- `npm run verify:journey-catalogue`
- `npm run verify:journey-runtime`
- `npm run verify:journey-orchestration`
- `npm run verify:journey-scenarios`
- `npm run lint`
- whole-project TypeScript validation
- `npm run build`

Where a controlled regeneration is required, run `npm run generate:journey-intelligence` only after the operational input and output targets have been verified. Run the complete existing `verify:journey-*` / `generate:journey-*` suite before final promotion, as required by the approved plan's WP-11 regression discipline.

### 10.3 Regression comparison

The before/after comparison must include:

- generated artefact filenames, record counts, and checksums;
- candidate and region identity sets;
- per-candidate Emotion IDs;
- per-candidate Theme IDs;
- per-candidate Traveller Type suitability;
- fallback behaviour, including default Emotion handling;
- deterministic output across two equivalent generator executions;
- representative traveller-profile recommendation results; and
- confirmation that Journey Passport, navigation, homepage, and unrelated flows are unchanged.

## 11. Risk Register

| Risk | Severity | Mitigation | Rollback / disposition |
| --- | --- | --- | --- |
| Generated mappings change Emotion, Theme, or Traveller Type assignments for existing candidates and alter traveller-facing recommendations | **Medium–High** | Mandatory semantic diff; Product review of every existing-candidate change; Archie review before promotion | Retain the pre-change mapping tables and generated artefact baseline; restore the prior mapping/output set if changes are not approved |
| Reconciliation findings expand the known operational gap and create unplanned implementation scope | Medium | Report findings; do not silently author rows or change business status; route new gaps to Tiger/Vivek | No code rollback required when the check is working correctly; disposition findings separately |
| Warn-mode becomes a permanent ignored warning channel | Medium–High | Named non-suppressible report section, explicit owner/status fields, and promotion-review checklist | Promotion remains blocked for unexplained findings even though generation completes |
| KB parsing or identity matching creates false gaps | Medium | Use stable identifiers; test destination and region cases; make comparison results reviewable | Disable promotion and correct the focused reconciliation logic; do not weaken the check globally |
| Mapping generation introduces unsupported runtime IDs | Medium | Type-check targets and fail focused generation before artefact promotion | Keep existing tables active until corrected and approved |
| Generated output becomes non-deterministic | Medium | Run existing determinism verification and enforce stable ordering | Revert the focused generator change; retain the last verified artefact set |
| Scope drifts into schema, runtime, or registry work | High governance risk | Use §13 as a hard boundary; Archie reviews planned and actual files | Stop implementation and issue a separate architecture / Product proposal |
| Operational workbook and generated artefacts remain intentionally out of sync | Medium | Record checksums and regeneration timing; promote only a matched, verified pair | Continue serving the previous verified generated package until the controlled regeneration is approved |
