## Phase B — Implementation

**Approach.** WP-4's own text is specific: compare every KB §10/§11 `ACTIVE` destination/region against the operational layer's row set; extend `validateWorkbook.ts`'s neighbourhood rather than replace it; extend `writeGenerationReport.ts` with a named, non-suppressible section distinct from `REVIEW_REQUIRED` warnings; add a promotion-review checklist step (ADR §9); operate in Warn Mode (`DEC-R1.2-015`) — never throw, never block generation.

**KB data source (`kbApprovedPortfolio.ts`).** The KB's own portfolio tables (§10.1, §11.1) list exactly 24 `ACTIVE` entries — 17 domestic, 7 international — matching the count both prior Rad audits and the ADR (Appendix A) independently converged on ("22 of 24..."). Two of the 17 domestic entries are the KB's own explicitly-named `Collection` record type (§7.3): **Northeast** (members: Meghalaya, Sikkim, Darjeeling — grouped from KB §10.11's five named member-region rows by their leading place name, since the operational layer does not currently sub-divide within a member place) and **Wildlife** (members: Kabini, Corbett, Bandipur, Masinagudi — KB §10.18). All other 22 entries are reconciled at destination level only. This boundary was a deliberate scope decision, not an oversight — see "Follow-up recommendations" below.

**The check (`validateKbReconciliation.ts`).** A pure function, `reconcileKbToOperational(model)`, taking the already-loaded `WorkbookModel` and returning a report (`mode: "WARN"`, counts, `findings[]`). It never throws. Matching is mechanical: destination/region names are compared case- and whitespace/punctuation-insensitively (`"TamilNadu"` and `"Tamil Nadu"` correctly match; no semantic aliasing — e.g. it does **not** assume `"Wildlife Tours"` means the same thing as `"Wildlife"`, since deciding that is a business judgement outside Rad's authority, not a mechanical normalisation). Two finding codes: `KB_DESTINATION_ABSENT` and `KB_MEMBER_REGION_ABSENT`.

**Wiring (`index.ts`).** The check runs immediately after `validateWorkbook`, before artifact generation begins, and its report is threaded through to `writeGenerationReport`. It does not gate, delay, or alter generation in any way — this matches Warn Mode exactly.

**Reporting (`writeGenerationReport.ts`).** Added a new `## KB → Operational Reconciliation (WP-4)` section, always rendered (even when there are zero findings, so it cannot be silently suppressed), positioned after the existing Warnings subsection and before Determinism. Added a `## Promotion Review Checklist (ADR §9)` section reminding whoever promotes a new generated package that a destination-inclusion or vocabulary-reach change requires Product & Experience approval before promotion; routine content refresh does not.

**Documentation (`JOURNEY-INTELLIGENCE-GENERATOR.md`).** Added the new step to the numbered production sequence and a short subsection explaining the check, its Warn Mode status, and its current region-level coverage boundary (Northeast/Wildlife only).

**No other file was touched.** `generateJourneyDNA.ts`'s inclusion filter, the engine, the adapter, the operational workbook, and every controlled-vocabulary type were not modified, per this EBC's explicit Out of Scope list.

**A pre-existing, unrelated regression blocked full end-to-end generation.** `validateWorkbook.ts` (existing code, not touched by this EBC) failed with `Compatibility Matrix region IDs must be unique` before the new reconciliation check ever ran. Investigation (not a workbook edit — read-only): every one of the Compatibility Matrix sheet's 107 rows has its `Destination ID`/`Region ID` cells implemented as **live cross-sheet formulas** (e.g. `='Destination Intelligence'!B2`), and every one of those formulas is currently missing its cached value in the underlying XML — confirmed identically by both a direct Python/openpyxl read and this repository's own `loadWorkbook.ts` (which reads cached values from the raw sheet XML via `unzip`, not a formula-evaluating library). With no cached value, all 107 rows resolve to the same blank `Region ID`, tripping the uniqueness check.

**Root cause, most likely:** this is a side effect of the workbook edit performed in `EBC-R1.2-03.08B` (Phase 1B, commit `7022917`) — that edit deliberately loaded the workbook **without** `data_only=True` specifically to preserve formula *text* (correctly verified at the time: formula cell count was unchanged, 3,959 before and after). What was not checked at the time is that `openpyxl`, when saving a workbook loaded in formula-preserving mode, does not carry forward previously cached formula *values* — a known library limitation, not specific to any cell that edit actually touched. This explains why the effect is workbook-wide (all 107 rows, not only the 2 rows Phase 1B edited) and why it was invisible until now: **`generate:journey-intelligence` had never been run against the post-Phase-1B workbook until this session** — the last successful generation report (`outputs/ebc-003c-b/JOURNEY-INTELLIGENCE-GENERATION-REPORT.md`) and `web/generated/metadata.json` both still record the *original*, pre-Phase-1B workbook checksum (`b90a6af3...`), confirming no one has regenerated since.

**This is not caused by, and is not part of, WP-4.** WP-4's own code never touches the Compatibility Matrix sheet or any formula. To confirm WP-4's deliverable is correct independent of this blocker, I ran it directly against the real, loaded workbook, bypassing only the unrelated `validateWorkbook` step:

```
mode: WARN
destinationsChecked: 24
memberRegionsChecked: 7
findings: 9
```

Findings: `Northeast — Darjeeling` absent (matches the known, already-documented deferred item); `Hyderabad`, `Vizag`, `Dubai` entirely absent from the operational layer under any matching name; `Wildlife` absent under that exact name (the operational layer uses `"Wildlife Tours"`, which the check correctly does not treat as an automatic alias — see follow-ups) with its 4 members (Kabini, Corbett, Bandipur, Masinagudi) consequently also reported absent, since none can be located under a destination the check couldn't match. All 22 remaining KB-approved entries — including Assam, Amritsar, and the Northeast members it can match (Meghalaya, Sikkim) — correctly produced **no** finding, and `TamilNadu`/`Tamil Nadu` correctly matched despite the spacing difference. This is exactly the check WP-4 specifies, working correctly.

### D. Risks

**Residual risk within WP-4's own scope: none identified.** The check is additive, throws never, and cannot alter generated output or runtime behaviour.

**Blocking risk outside WP-4's scope, discovered during this EBC, escalated per Section 10:**
- **Evidence:** all 107 Compatibility Matrix rows have blank cached formula values for `Destination ID`/`Region ID`, tripping `validateWorkbook.ts`'s existing uniqueness check; the last successful generation predates the Phase 1B workbook edit; the formulas' text is intact, only their cached results are gone — consistent with a known `openpyxl` save-mode limitation, not data loss.
- **Impact:** `npm run generate:journey-intelligence` cannot currently complete successfully against the current workbook, for **any** reason — this blocks WP-4's own end-to-end run, WP-5, and any future regeneration, not merely this EBC.
- **Recommendation:** the workbook needs its formulas recalculated and cached values re-saved by a real calculation engine — not by further `openpyxl` edits, which cannot compute formulas. This is a workbook remediation task, squarely within the Destination Operational Steward's ownership (ADR §8), not a generator change, and is explicitly Out of Scope for WP-4 ("Do not introduce... Generator redesign," "avoid unrelated refactoring"). I have not applied this to the real repository workbook — only proven it, below, on disposable test copies.
- **Proof (performed on disposable test copies only; the real `outputs/ebc-003c-a/Journey Director Intelligence Enriched.xlsx` was never written to — its checksum, `17d4c5a5...`, is unchanged before and after this investigation):**
  1. Headless LibreOffice recalculation alone (`soffice --headless --convert-to xlsx:"Calc MS Excel 2007 XML"`) resolved the original failure — `validateWorkbook.ts`'s "Compatibility Matrix region IDs must be unique" check passed, with formulas left as live formulas (verified: `='Destination Intelligence'!B2` still a formula, not flattened).
  2. Running `generate:journey-intelligence` against that recalculated copy then surfaced a **second, distinct, pre-existing issue**: two static (non-formula) "Reason Reference" cells in the Compatibility Matrix sheet, for exactly the two rows `EBC-R1.2-03.08B` restructured (`india-assam-assam`, `india-assam-kaziranga`), still held the *old* region IDs (`india-northeast-assam`, `india-wildlife-tours-assam`) — that edit updated the Destination Intelligence sheet's identity fields but never touched this separate, literal cross-reference column.
  3. Correcting those 2 cells (via `openpyxl`, which — as expected and independently reconfirmed — again stripped all cached formula values workbook-wide) and re-recalculating via LibreOffice, then rerunning generation, surfaced a **third, related, pre-existing gap**: the Review Register sheet's `Region ID` column for review items `review-0135`, `review-0206`, `review-0285`, `review-0286` (the same four items `EBC-R1.2-03.08B` marked "Resolved") also still held the old region IDs, tripping `validateWorkbook.ts`'s "Review-required records must appear in the Review Register" check for `india-assam-assam`.
  4. Correcting those 4 cells and recalculating once more produced a **full, clean pass**: `npm run generate:journey-intelligence` completed end-to-end (12,925 validation checks passed, 17 pre-existing unrelated warnings, WP-4's KB Reconciliation ran and reported its 9 already-documented findings, all 8 runtime artifacts generated and verified, determinism skipped only because `--skip-determinism` was passed for a faster test run — not itself evidence of a problem).
  - **Answer to "does recalculation alone resolve it": no.** Recalculation is necessary and correctly diagnosed as the root cause of the *original* failure, but it is not sufficient on its own — two further, narrowly-scoped, genuine data gaps in `EBC-R1.2-03.08B`'s edit (2 Compatibility Matrix cells, 4 Review Register cells, all confined to the same Assam rows that edit touched) also need correcting. No code change was involved in reaching a clean pass; all three fixes were workbook data corrections.
- **Whether Archie or Tiger review is required:** recommend Tiger sequence a small, explicitly-scoped follow-up EBC — recalculation plus these 6 specific cell corrections, all confined to the rows `EBC-R1.2-03.08B` already restructured — to apply this proven fix to the real repository workbook. Destination Operational Steward authority (Rad) is sufficient to execute it once scoped; no new architecture decision is needed, since this completes an edit already approved and performed, rather than changing business content, vocabulary, or architecture. No Archie review is required for the fix itself on that basis.
