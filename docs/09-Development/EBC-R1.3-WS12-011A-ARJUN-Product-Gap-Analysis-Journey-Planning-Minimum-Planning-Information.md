## Background (restated for record)

Product Owner Acceptance (WS12-011) found no engineering or functional defect — WS12-009/010's QA cycle is closed. The Product Owner instead identified a **business capability gap**: the Create Record screen (Record Type, Title, Origin Channel, Destination Region, Traveller/Corporate identification) is technically sufficient to create a Journey Planning Record, but operationally insufficient for an ops executive to begin itinerary design. The Product Owner's own candidate minimum-information list: Traveller Composition (Adults/Children/Infants), Travel Timing (Intended Month; Intended Date where known), Journey Duration (Nights/Days), Preferred Departure City — with Budget explicitly and deliberately excluded, to remain a later, consultative discovery rather than a mandatory upfront input.

This card's instruction is explicit: **analyse, don't just add fields.** What follows validates the assumption, traces downstream impact, assigns ownership, sequences the lifecycle, and drafts (not applies) the resulting specification changes.

## 1. Validating the Product Owner's Assumption

### 1.1 This is not a new idea — it is an existing, unimplemented commitment, more loosely worded

`EBC-R1.3-WS12-003` §7, `FR-JP-12` (already Product-Owner-approved, part of the original 30) reads:

> *"The Owner shall be able to capture and edit traveller requirements against a Journey Planning Record: destination, travel dates, date flexibility, duration, budget, companions, special requests, flight preferences."*

The Product Owner's new list is a **more specific, more structured decomposition** of exactly this — "companions" becomes Adults/Children/Infants; "travel dates"/"date flexibility" becomes Intended Month/Intended Date; "duration" becomes Nights/Days. Confirmed by repository inspection (Section 0): none of `FR-JP-12`'s fields — including the vague, already-approved ones — exist anywhere in the current implementation (`types.ts`, `JourneyPlanningRecordDetailView.tsx`: zero matches for companions/budget/duration/travel-date). So the underlying capability was never built at any lifecycle point, not merely omitted from the creation screen. **This is a genuine, real gap — the Product Owner's operational concern is correct** — but it is best understood as "finish implementing an existing approved requirement, with sharper field definitions," not as new scope invented at acceptance time.

**One explicit exception, and it is intentional, not an oversight:** `FR-JP-12` lists Budget as something the Owner "shall be able to capture" — a permitted capability, not a mandatory one. The Product Owner's new instruction to keep Budget out of the *minimum* set does not contradict `FR-JP-12`; it clarifies that Budget remains optional and consultative, never structurally required. This mirrors the existing pattern at `FR-JP-13` ("Journey Planning shall not require a 'purpose of travel' field") and at the traveller-facing Journey Passport's own stated philosophy (`JOURNEY-PASSPORT-v1.0.md`: *"Uncertainty, flexibility, companion type, destination knowledge and future budget must never become status signals"*). Recommendation: make this exclusion explicit as its own Functional Requirement (Section 5.1, proposed `FR-JP-32`), the same way `FR-JP-13` made the purpose-of-travel exclusion explicit, rather than leaving it as an implicit reading of what a "minimum" list omits.

### 1.2 No upstream channel currently supplies this data automatically

Checked whether any origin channel already carries this information, so it could be pre-populated rather than manually entered. Finding: **no.** The Journey Passport (the only automated intake channel, feeding "Website enquiry" origin) captures companion *type* — a qualitative social-context signal ("Solo," "Couple," "Family," "Friends" — `JOURNEY-PASSPORT-v1.0.md`: *"Principal group character, not a full passenger list"*) — not a numeric Adults/Children/Infants breakdown, and repository search (`web/lib/journey-leads/`) confirms no such numeric fields exist in the lead schema today. Practical consequence: **every origin channel, Website enquiry included, requires the Workspace Owner to capture this information fresh** — no channel-specific pre-population logic is needed for this gap (a simplification worth confirming explicitly, since it removes one source of complexity the Product Owner may not have had visibility into).

## 3. Information Ownership

The central ownership question this gap analysis resolves: **is this information about the Traveller, or about this specific trip?** It is about the trip. The same Traveller can plan a solo weekend one year and a family holiday with two children the next — Adults/Children/Infants counts, timing, duration and departure city are properties of *this planning effort*, not durable facts about *the person*. Confirmed against `EBC-R1.3-WS12-003` §6.5: Traveller is "referenced not owned by Journey Planning" (`PD-JP-004`) — this analysis does not disturb that boundary; it reinforces it by keeping trip-specific data out of the Traveller object entirely.

| Field | Owning object | Rationale |
|---|---|---|
| Number of Adults | **Journey Planning Record** | Per-trip, not per-Traveller (Section 3, opening) |
| Number of Children | **Journey Planning Record** | Same |
| Number of Infants | **Journey Planning Record** | Same |
| Intended Travel Month | **Journey Planning Record** | Same; also aligns with `FR-JP-12`'s existing "travel dates" scope |
| Intended Travel Date | **Journey Planning Record** | Same |
| Number of Nights (source of truth) | **Journey Planning Record** | Same |
| Number of Days (derived, not stored independently — Section 1.3) | **Journey Planning Record** (computed) | Avoids a second source of truth |
| Preferred Departure City | **Journey Planning Record** | Same; logistics input, not identity |
| Traveller (name, email, phone) | **Traveller Hub (referenced)** | Unaffected by this analysis — durable person-level identity, correctly out of Journey Planning's ownership already |
| Proposal / Proposal Version | **No new fields** | Consumes these values transitively via the Itinerary it references (Section 2) |
| Itinerary (future, Itinerary Studio) | **Consumes, does not own, the source values** | The itinerary is *built from* Nights/Days/Departure City; those values remain owned by the Journey Planning Record they were captured against, referenced rather than copied, to prevent drift between a JP Record's parameters and the itinerary authored against them |

## 4. Lifecycle Analysis — Lifecycle Requirement Matrix (Revised, Revision 1)

**Superseded by this revision:** the original Section 4 recommended against introducing any system-enforced Discovery-exit gate, on the basis that `EBC-R1.3-WS12-003` §5's discretion-based design ("a business judgement, not a system-enforced field count") was sound as-is. The Product Owner's clarification changes this: Children/Infants composition materially affects room allocation, vehicle selection and pricing, and the Product Owner wants the system to guarantee that composition is *known* (not merely "available to enter") before itinerary work starts, rather than leaving that guarantee to individual Owner discretion. This is not a reversal of `EBC-R1.3-WS12-003` §5's design principle — Discovery's exit remains a business judgement in general — it is the introduction of one narrow, named precondition that judgement must satisfy before it can be exercised. Superseded text is retained in the repository's version history (supersede-not-erase convention), not deleted.

The table below replaces the flat Mandatory/Optional framing with a stage-by-stage view: **Available From** (when the field can first be populated), **Explicit Value Required By** (the lifecycle point past which an unanswered field blocks progression), and **Gate Type** (whether that point is creation-blocking, a stage-transition gate, or unenforced/discretionary).

**Data-integrity precondition for every gate above (proposed `BR-023`):** a stage-transition check of the form "Children must have a value" is only meaningful if the system can distinguish an **explicit, confirmed zero** from **not yet asked**. A Children/Infants field that silently defaults to 0 on creation would make every record appear to already satisfy the Discovery→Planning gate, regardless of whether the Owner ever asked the question — defeating the purpose of the gate entirely. Section 5.4 details the required tri-state behaviour (unanswered / explicit zero / explicit positive count). The same principle now also governs Departure City as of Revision 2 — an unset departure city must not be confusable with any placeholder or default string value.

### 5.2 Proposed Business Object Update — `EBC-R1.3-WS12-003` §6.1, Journey Planning Record

**Revision 1 note:** Number of Children and Number of Infants must each be capable of storing three distinct states — unanswered, explicit zero, explicit positive count — not the usual two (see Section 5.4's tri-state requirement, `BR-023`). A schema that represents "no children" and "not yet asked" with the same stored value (e.g., a bare integer defaulting to 0) cannot support the `FR-JP-34` gate correctly, since it would make every newly created record appear to already satisfy it.

**Revision 2 note:** the same tri-state integrity requirement now also applies to Preferred Departure City (an unset value must not be confusable with a placeholder or default string) since it joined the same gate. Intended Travel Date carries no gate within this module at all — its future mandatory point belongs to WS13 Journey Workspace and is out of scope for this card's own data model.

Modelled as a distinct, named sub-group (not flattened into the record's top-level identity fields) so that a future schema can extend it (e.g., a multi-room breakdown) without disturbing the record's core identity — flagged for Archie's judgement if and when this is formally adopted, not decided here.

## 6. Recommendations Summary (Revised, Revision 2)

- **Required at record creation (creation-blocking):** Number of Adults only (`FR-JP-31`, unchanged).
- **Present as fields from creation, but not creation-blocking; explicit value (zero permitted for the numeric fields) required before the record leaves Discovery for Planning:** Number of Children, Number of Infants, Intended Travel Month, Number of Nights, **and Preferred Departure City** (`FR-JP-33`/`34`, `BR-021` — Departure City added in Revision 2, resolving `OQ-011A-5`; no separate later gate remains).
- **Fully discretionary throughout Journey Planning's own lifecycle — no gate within this module:** Intended Travel Date. **Product Owner decision, Revision 2:** becomes mandatory only at the booking/confirmation stage, a stage outside Journey Planning's seven-stage lifecycle and flagged to WS13 Journey Workspace (`FR-JP-36`, `BR-024`) — not built or gated here.
- **Not tracked as an independent field at all:** Number of Days — derive from Nights; revisit only if the Product Owner confirms a real case for them to diverge (`OQ-011A-1`, unchanged).
- **Explicitly and permanently excluded from structured mandatory capture, at any stage:** Budget (`FR-JP-32`, unchanged).
- **Validation:** Adults integer ≥ 1 (creation-mandatory); Children/Infants integers ≥ 0, with the unanswered state stored and validated as distinct from an entered zero, not defaulted (`BR-023`); Nights integer ≥ 0 with the same explicit-value requirement; Departure City non-blank — all five checked together at the single Discovery-exit gate as of Revision 2.
- **Business-level UI behaviour (not a design — Sophie's territory to implement):** record creation adds exactly one new required input (Adults); Children, Infants, Travel Month, Nights and Departure City should be presented as an easily accessible, low-friction panel available the moment the record exists, with the system withholding progression to Planning (not withholding record creation) until all five hold an explicit answer; Travel Date carries no such prompt within this module at all.
- **Future extensibility:** model Planning Parameters as a distinct sub-group on the Journey Planning Record (Section 5.2), not flattened fields, so a future refinement (e.g., a room-by-room composition breakdown) is additive rather than a rework.
- **One system-enforced stage-transition gate now stands, where none existed before Revision 1 — not two.** Revision 1 introduced a Discovery-exit gate (Children/Infants/Month/Nights) plus a separate, later Planning-exit gate for Departure City; Revision 2 collapses these into a single, expanded Discovery-exit gate covering all five fields, per the Product Owner's decision. `EBC-R1.3-WS12-003` §5's general "Discovery-exit is a business judgement" design is still not reversed — these five named preconditions are additional requirements within that judgement, not a replacement for it.

## 8. Final Recommendation (Revised, Revision 2)

- **Discovery→Planning gate (single, expanded — `FR-JP-34`/`BR-021`):** Number of Children, Number of Infants, Intended Travel Month, Number of Nights and Preferred Departure City must each hold an explicit value before a record may leave Discovery for Planning. - **Unchanged since the original analysis:** `FR-JP-31`/`32`, `BR-020` (Adults creation-mandatory; Budget permanently excluded), and `BR-023` (explicit-value/tri-state data integrity, now also covering Departure City).
