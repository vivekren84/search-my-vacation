## Phase B — Implementation

**Approach.** The governed label→runtime-ID mapping cannot be mechanically derived from workbook text alone — it encodes a product naming decision (e.g. the workbook's "Explore" label maps to the runtime's `curiosity` emotion; "Healing" and "Slow Living" both map to `serenity`; "Wildlife" maps to two theme IDs, `wildlife` and `safari`). `labelMappingSource.ts` therefore holds this mapping as an explicit, curated, unchanged transcription of what was previously hand-typed directly inside `release1Candidates.ts`, alongside a mechanical transcription of the full `EmotionId`/`ThemeId`/`TravellerType` runtime unions (needed to compute reachability without importing application runtime code into the generator's separate TypeScript project — the same pattern `kbApprovedPortfolio.ts` already established for WP-4's KB transcription).

`generateLabelMappings.ts` (a new, additive generation step, run immediately after Journey Template generation and before artifact writing) cross-references this governed mapping against the operational layer's current `travellerTypes`/`emotionalGoals`/`desiredExperiences` on every generation run, and produces three things: the generated tables themselves (restricted to labels the operational layer actually carries today, so a future workbook change is reflected automatically rather than silently ignored); comparison findings (`LABEL_WITHOUT_MAPPING` for an operational label with no governed entry, `MAPPING_WITHOUT_OPERATIONAL_LABEL` for a governed entry whose label has disappeared from the workbook); and reachability findings for each vocabulary (how many of the full runtime type's values are reachable through at least one current mapping entry).

Rather than introduce a ninth generated JSON artifact — which the prior EBC (`R1.2-WS3-IMP-01B`, Finding 2) found breaks `verifyArtifactPackage`'s "exactly the eight documented artifacts" check the moment a second file/directory coexists in `web/generated/` — this data is folded into the existing `metadata.json` artifact as a new `labelMappings` field. This reuses the same fail-closed-verified path every other constant in `release1Candidates.ts` already reads through (`runtimeJourneyIntelligence`), adds zero new files to verify, and avoids that known trap entirely. I confirmed before implementing that neither `verifyArtifactPackage` (generator-side) nor `loadRuntimeIntelligence.ts`'s `verifySource` (runtime-side, fail-closed) perform an exact-key-match check on `metadata.json`'s own shape — both only assert specific known fields — so this addition could not silently break either verification path; live validation below confirms this held.

`release1Candidates.ts` now reads `EMOTION_BY_LABEL`/`THEMES_BY_LABEL`/`TRAVELLER_BY_LABEL` from `runtimeJourneyIntelligence.metadata.labelMappings`, narrowed to this file's literal-union types via the same type-assertion pattern `loadWorkbook.ts` already uses for workbook-sourced string fields (e.g. `get("Travel Scope") as TravelScope`). The mapping values themselves, and every downstream function that consumes them (`themesFor`, `emotionsFor`, `bestFor`), are unchanged — only the tables' origin moved from an inline literal to generated, validated data.

**Key technical decisions:**

1. **Fold into `metadata.json` rather than add a new artifact** — smallest footprint, reuses the existing fail-closed verification path, avoids the known "exactly eight artifacts" fragility.
2. **Keep the governed mapping values as a curated input, not a derived one** — the workbook states labels, not runtime IDs; deriving IDs mechanically would require guessing a naming convention the actual mapping does not follow (e.g. "Healing" → `serenity`, not `healing`). This preserves "no runtime redesign" and "preserve existing runtime behaviour" exactly.
3. **Do not extend either vocabulary** — OD-4 (Traveller Type) is confirmed unresolved; Emotion/Theme have no equivalent named open decision but are governed by the same principle (WP-3 has not grown the taxonomy sheets). The generated tables at today's scope are therefore identical in content to the previous hand-authored tables — this is proven, not assumed, in Phase C below.
4. **Do not touch `engine.types.ts`** — extending the `TravellerType`/`EmotionId`/`ThemeId` unions is a type-level architecture change requiring Archie's approval (Project Instructions §5/§21), and is exactly what Open Decision OD-4/OD-8 (`EBC-R1.2-03.05` §12) reserve for a future, separate decision.
