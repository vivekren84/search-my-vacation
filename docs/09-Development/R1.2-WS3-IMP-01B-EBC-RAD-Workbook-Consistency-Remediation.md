### Finding 1 — Device-bridge FUSE limitation on the generator's own backup cleanup (environment-only, not a code or data defect)

`generate:journey-intelligence`'s atomic-swap step renames the new package into place, then attempts to `rm()` the now-stale backup directory. On this device-bridge mount, `rm`/`unlink` on generator-created temp/backup directories fails with `EPERM: operation not permitted`. This was reproduced three times with different process IDs, and in every case the artifact swap-in itself had already completed successfully before the cleanup step failed (confirmed via `metadata.json`'s updated checksum and timestamp each time). This is a per-run, deterministic characteristic of running Node's `fs.rm` against this specific FUSE-mounted path — not a defect in the generator, the workbook, or this remediation.

I verified correctness independently of the failing cleanup step: the artifacts actually swapped into `web/generated/` were diffed and are **byte-identical** to a fully clean run written to an isolated `/tmp` path (which completed end-to-end including verification = 17,455/17,455 checks and determinism = PASS). `web/generated/metadata.json` in the real repository shows `workbookChecksum: "868271e5..."` and a fresh `generatedAt`, confirming the in-place package is current and correct.

Each occurrence of a stale `.journey-intelligence-backup-*` directory blocking a subsequent run was cleared via `mv` into `_to_delete/` (device_bash cannot `rm`, but `mv` succeeds). This will recur on every future regeneration performed through this device-bridge path; it is not something this EBC's scope permits fixing (would require generator code changes, explicitly out of scope), and it does not affect the correctness of the artifacts actually produced.

### Finding 2 — `verify:journey-intelligence` "exactly the eight documented artifacts" check (pre-existing, not a regression)

A separate, independently-scoped generator (`generate:journey-itineraries`) writes a `journey-itineraries/` subdirectory into `web/generated/`. The journey-intelligence generator's atomic swap replaces the *entire* `web/generated/` directory and never includes that subdirectory in its own temp output, so running `generate:journey-intelligence` silently drops `journey-itineraries/`.

I detected this only because it broke `tsc --noEmit` (4 `Cannot find module` errors from `lib/journey-itineraries/loader.ts` and `verifyItineraryRuntime.ts`). I restored `journey-itineraries/` from the preserved pre-swap backup and confirmed byte-identical restoration via `git status` (zero diff on that path). This was necessary to avoid a genuine, unreported regression outside the Assam restructuring — leaving it dropped would itself have been an out-of-scope, unrelated change this EBC's own risk section explicitly warns against.

That restoration is what makes `verify:journey-intelligence`'s standalone `readdir`-based "exactly eight" check fail — `web/generated/` now (correctly) contains nine entries once `journey-itineraries/` coexists. I confirmed this check (`verifyArtifactPackage` in `verifyArtifacts.ts`) is the same function used internally by the full pipeline and by the standalone script, and that it has no allowance for the two generators' outputs coexisting. This is a pre-existing architectural gap — two generators unsafely sharing one output directory — that predates this remediation; it was simply never exercised before because `journey-itineraries/` and a completed `generate:journey-intelligence` run had not previously coexisted in a state anyone re-verified. Fixing it would mean changing generator or verification-script code, which is explicitly out of scope for this EBC. I am reporting it, not fixing it.

### Finding 3 — `verify:journey-intelligence:steering` "mountain intent keeps Goa eligible" failure (pre-existing, confirmed unrelated)

I proved this is unrelated to the Assam remediation by diffing every regenerated artifact against its pre-remediation git-tracked version:

- `compatibility-matrix.json`: the **only** difference is the `workbookChecksum` footer. Zero score data changed — Goa's compatibility values are byte-identical before and after.
- `journey-dna.json`: the only content differences are Assam/Kaziranga hierarchy-reference records (moving from incorrect parents `india-northeast` / `india-wildlife-tours` to the correct `india-assam`), all of which carry `recommendationEligible: false` both before and after — they were never eligible for scoring. No Goa record, and no mountain-candidate record (Meghalaya, Sikkim, Darjeeling, or any other), changed at all.
- `constraint-library.json`: the only differences are the `target` region-ID correction on the same two Assam/Kaziranga `REVIEW_REQUIRED`-sourced constraint rows. No Goa or mountain-candidate constraint entries touched.
- `journey-seeds.json`, `journey-templates.json`, `reason-library.json`: each shows only the `workbookChecksum` footer changed.

Since Goa's own data and every mountain-tagged candidate's data are provably untouched by this remediation, this steering-verification failure is pre-existing and unrelated — consistent with how `verify:journey-engine`'s known `moodValues` fixture issue was characterized earlier in this engagement. Root-causing the actual scoring-logic defect is outside this EBC's scope (no generator or runtime-code changes authorized here); it should be logged separately for Engineering follow-up.

### Finding 4 — `verify:journey-engine` (reconfirmed pre-existing, unrelated)

Failure message this run: `"escape resolves to its editable mood preselection"`. Source inspection confirms this is the same previously-documented issue: a hard-coded `moodValues` fixture array with only 5 entries against 6 `JOURNEY_FEELINGS`, causing an index-misalignment assertion failure on one feeling per run (this run: "Tropical Escape"). This is a UI mood-preselection fixture issue, entirely unrelated to destination or workbook data, and was already known and documented as pre-existing before this EBC began.

### Finding 5 — `npm run build` (reconfirmed pre-existing, unrelated)

After clearing an unrelated stale `.next/.fuse_hidden*` artifact (same device-bridge FUSE `unlink` limitation as Finding 1, cleared via `mv`), the project-wide build fails purely on `next/font`'s attempt to fetch Inter and Poppins from Google Fonts over the network — this sandbox has no network access to `fonts.googleapis.com`. This is a known, previously-documented environment limitation, unrelated to this remediation or to any code in this repository.

### Residual risks

1. **Device-bridge FUSE `unlink` limitation** will recur on every future `generate:journey-intelligence` run executed against this device-mounted path. It does not affect artifact correctness but will always cause the process to report FAILED and leave a stale backup directory requiring manual `mv` cleanup. This is an environment characteristic of this session's device bridge, not a repository defect.
2. **`journey-itineraries/`-sharing architectural gap**: two independently-scoped generators write into the same `web/generated/` directory, and the journey-intelligence generator's atomic swap does not account for the other generator's output. This will silently drop `journey-itineraries/` on every future `generate:journey-intelligence` run unless someone remembers to restore it, and `verify:journey-intelligence`'s "exactly eight artifacts" check will keep failing for as long as both outputs coexist. This needs a real generator-design decision (recommend routing to Archie/Arjun as a follow-up item) — explicitly not resolved in this EBC.
3. **`verify:journey-intelligence:steering` root cause** ("mountain intent keeps Goa eligible for scoring rather than hard-excluding it") remains unfixed. I have proven it is unrelated to this remediation, but the underlying scoring-logic defect is real and should be logged as a separate Engineering item.
4. **`verify:journey-engine`'s `moodValues` fixture** remains a known, unfixed pre-existing test-data issue (5 entries for 6 `JOURNEY_FEELINGS`).
5. **`_to_delete/` accumulation**: this session's device-bridge workarounds (moving files instead of deleting them, since `rm`/`unlink` is not permitted on the mount) have accumulated a number of stale backup directories, tarball staging artifacts, and a stale `.next` build directory under a top-level `_to_delete/` folder, which git shows as untracked. None of it is part of any deliverable. Recommend the user delete this folder directly from their own machine (outside the device bridge) at their convenience.
6. **Unrelated pre-existing repository state observed, not investigated further**: `git status` shows `docs/02-Product/EBC-007-JOURNEY-SCENARIO-AUDIT.md` as modified and two untracked prior-engagement reports (`EBC-R1.2-03.08-RAD-Phase-1-Business-Operational-Alignment-Implementation.md`, `EBCR1.2-009-EXPERIENCES-RETIREMENT-IMPLEMENTATION.md`).
