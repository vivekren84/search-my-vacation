### 5.2 B.3 Fallback — Rad's view

**I accept Archie's fallback as satisfying my C-4, and I withdraw my fallback wording.** Reasons:

1. **Atomic, where mine was not.** Archie's single execution (`begin;` + 12 drops + `delete from supabase_migrations.schema_migrations where version = '20261004100000'` + `commit;`) removes the functions and their history row together. My version ran §4.4 first and repaired the history later. In between, the remote history would have said M11 was applied (35 = 35) while the functions were gone, so `migration list` would have been misleading at exactly the moment the A.4 two-state rule depends on it.
2. **Needs no CLI.** This route exists for "CLI unavailable", and mine needed the CLI (`migration repair`) plus a new migration file written in a hurry.
3. **Same history change the CLI would make.** `migration repair --status reverted` deletes the version row (`DELETE_MIGRATION_VERSION`, `history.go:20`), so A.6 l.91's equivalence statement is correct. The result is the exact pre-deployment baseline: 34 remote, M11 local only.
4. **Fails safe.** If any statement fails, for example a missing privilege on `supabase_migrations` (the table was created by the CLI as `postgres`, `history.go:31-44`), the explicit transaction aborts and nothing changes.
5. **Its one risk is already caught.** The re-apply hazard ("do not run `db push` again until M11 is re-authorised") is covered beyond the instruction. Any later push would list `20261004100000` in its dry run, and step 6's "exactly the expected files" stop rule (A.4 l.62) would stop it.

Archie owns SR-01 parity, and on the technical merits her fallback is the better one.
